Résumé du projet "carnet"

Date : 12 février 2026

1) But du projet
- Application web (frontend + backend) pour gérer des nageurs et utilisateurs :
   - gestion des groupes, présences, évaluations et niveaux;
   - comptes utilisateurs (moniteurs, admin, clients) et authentification;
   - interface pour administrer les groupes de natation et de sauvetage.

2) État actuel du dépôt
- Structure principale :
   - `backend/` : API Node/Express, base SQLite, scripts serveur.
   - `frontend/` : pages HTML, CSS et scripts JS pour l'interface.
   - dossiers expérimentaux : `trop tot/`, `wtf/`.

Backend (points saillants)
- `server.js` : point d'entrée — prépare la base (appel `createTable` depuis `db.js`) puis démarre Express.
- `app.js` : configuration d'Express (JSON, logging, sessions via `express-session`, routes et fichiers statiques).
- `db.js` : utilise `knex` + `sqlite3` (fichier `basededonnees.sqlite3`) ; crée les tables `User` et `nageurs` si nécessaire et effectue un seed admin si absent.
- Fichiers utiles : `inspect_routes.js`, `requette.http`, `nodemon.json`, scripts dans `scripts/`.
- `package.json` et `package-lock.json` sont présents et `node_modules/` installé.

Frontend (points saillants)
- Pages principales : `login.html`, `register.html`, `client.html`, `admin.html`, `nageur.html`, etc.
- Scripts côté client dans `frontend/js/` et styles dans `frontend/css/style.css`.

3) Actions récentes
- Installation : `express-session` (ajoutée), tentative d'installation de `path` (module core — inutile).
- Audit : `npm audit` a signalé 7 vulnérabilités (1 modérée, 6 hautes).
   - Paquets impliqués : `cacache`, `lodash`, `make-fetch-happen`, `node-gyp`, `qs`, `sqlite3`, `tar`.
   - Recommandation : `npm audit fix` (ou `--force` pour tout corriger, mais risqué).

4) Problèmes rencontrés
- Vulnérabilités NPM : plusieurs vulnérabilités (dont des dépendances profondes). Nécessite une mise à jour planifiée et des tests.
- Erreur au démarrage : lors de `node server.js` une erreur système liée à la lecture de fichiers est apparue :
   Error: UNKNOWN: unknown error, read (errno -4094)
   - Causes probables : verrouillage/gestion OneDrive (chemin avec espaces/accents), permissions, ou chargement d'un binaire natif (`sqlite3`).

Détails techniques & diagnostic (instructions pas-à-pas)

1) Reproduire et capturer l'erreur Node (contexte Windows)
 - Depuis PowerShell, se placer dans `...\carnet\backend`.
 - Lancer Node en mode trace pour obtenir un stack plus complet :
    node --trace-warnings server.js
 - Si l'erreur n'est pas assez explicite, démarrer avec inspecteur pour pouvoir placer un breakpoint et voir l'étape du require :
    node --inspect-brk server.js
 - Vérifier si l'erreur survient avant que `server.js` n'affiche ses logs (si oui, c'est au chargement des modules).

2) Vérifications liées à OneDrive / fichiers verrouillés
 - Pause rapide de la synchronisation OneDrive : clic droit sur l'icône OneDrive → "Pause la synchronisation" (15 min).
 - Tester l'exécution depuis un chemin sans espaces/accents :
    - Copier le dossier `carnet` temporairement vers `C:\projects\carnet` et lancer `node server.js` depuis là.
 - Voir quels processus verrouillent des fichiers (Sysinternals): utiliser `Handle.exe` (optionnel) ou Resource Monitor → onglet "CPU" → Associated Handles.
 - Vérifier les permissions du fichier DB et des fichiers du projet :
    Get-Acl .\basededonnees.sqlite3 | Format-List

3) Vérifications liées aux binaires natifs (sqlite3)
 - Les erreurs `read` inconnues peuvent venir d'un binaire natif manquant/corrompu.
 - Réparer les modules natifs :
    - Supprimer `node_modules` et réinstaller proprement :
       rm -r node_modules; npm ci
    - Si `sqlite3` est problématique : `npm rebuild sqlite3`.
    - Pour forcer une version : `npm install sqlite3@5.0.2` (tester sur branche).

4) Logs et diagnostics supplémentaires
 - Inspecter le fichier `package.json` pour versions problématiques.
 - Lancer `node --trace-deprecation` ou `NODE_DEBUG=module node server.js` pour plus d'informations lors du chargement des modules.
 - Si le problème persiste uniquement dans OneDrive, privilégier l'exécution hors OneDrive.

Plan sécurisé pour corriger les vulnérabilités NPM

1) Workflow recommandé (sécurisé)
 - Faire un commit de l'état actuel :
    git add . && git commit -m "snapshot before audit fixes"
 - Créer une branche pour les fixes :
    git checkout -b fix/npm-audit-YYYYMMDD
 - Exécuter `npm audit fix` (non forcé) :
    npm audit fix
 - Exécuter la suite de tests (ou simplement démarrer le serveur et parcourir les pages principales) — valider le bon démarrage et tests manuels rapides.
 - Si des vulnérabilités restent et que les fixes recommandent des mises à jour majeures, planifier les mises à jour manuelles et les tester séparément (p.ex. `sqlite3@5.0.2`).

2) Actions spécifiques suggérées selon les vulnérabilités détectées
 - `lodash` : mettre à jour vers la version corrigée (vérifier la compatibilité des packages qui l'utilisent).
 - `qs` : mettre à jour vers >=6.14.1.
 - `tar`, `cacache`, `make-fetch-happen`, `node-gyp` : ces paquets remontent souvent depuis des outils (npm, fetch libs, node-gyp) ; la stratégie :
    - `npm update` et `npm audit fix`, puis parcourir la chaîne de dépendances pour identifier le paquet direct qui les exige et le mettre à jour.
 - `sqlite3` : si le fix propose `5.0.2`, tester la mise à jour sur branche et rebuild des binaires.

3) Validation après correctifs
 - Démarrer le serveur, faire un smoke-test des endpoints principaux.
 - Vérifier les logs et absence d'erreurs natives.
 - Re-run `npm audit` pour confirmer l'état.
